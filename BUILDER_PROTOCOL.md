# Протокол builders

Поставка публичных модулей и минимальный внешний builder: [INTEGRATION.md](INTEGRATION.md). Специальные сообщения макросов: [семантика builders](CE_SEMANTICS.md).

Таблица возможностей builders и общий контракт: [CE_SEMANTICS.md](CE_SEMANTICS.md).

Новый builder добавляется отдельным `.das`-модулем. Править `computation.das`
или регистрировать имя типа в макросе не нужно.

```das
require ./packages/computation/computation_macro.das
require ./examples/builders/reader_builder.das

let answer = computation(ReaderBuilder(7)) {
    let environment = reader_ask() |> bind
    return environment * 6
}
assert(answer.value == 42)
```

`computation.das` — совместимый фасад: подключает макрос и прежние стандартные
builders. Можно оставить `require computation` и дополнительно подключить свой
модуль. Для минимального набора зависимостей используйте `computation_macro`.
ReaderBuilder в библиотеку не входит: это пример из
[examples/builders](examples/builders/README.md), как и State, Writer и Query.
`reader_demo.das` показывает расширение только через два импорта; сам builder
требует лишь `builder_protocol`.

## Имена псевдонимов типов

В обобщённых операциях builder псевдонимы типов называйте как в daslib:
`auto(TT)`, `auto(EE)`, `auto(ItemT)`, а не `auto(T)`. Обобщённая функция
компилируется в модуле, который её вызывает, и видимый там тип побеждает
псевдоним с тем же именем. dastest экспортирует классы `T` и `B`, поэтому
операция с `auto(T)` не компилируется в файле теста.

## Выбор стратегии

В модуле builder определите перегрузку `ce_protocol(builder)`:

| Возвращаемый тип | Раскрытие |
| --- | --- |
| `CeValueProtocol` | Синхронное вычисление с копируемым результатом; Bind/Combine решают, выполнять ли продолжение |
| `CeDirectProtocol` | Value-builder, у которого Bind и Combine только обрывают вычисление; раскрывается напрямую, без продолжений (см. «Прямое раскрытие») |
| `CeOwnedProtocol` | Перемещаемые результаты, consuming bind с временным заимствованием payload; см. [семантика builders](CE_SEMANTICS.md) |
| `CeCollectProtocol` | Накопление результатов, `yield`, `yield_from`, перемещение результата и `inscope` для промежуточных коллекций |
| `ce_sequence_protocol(type<T>)` | Ленивый native generator элементов T; завершается вызовом `ce_sequence_run(builder, source)` |

Это номинальные дескрипторы из `builder_protocol`, а не совпадение строкового
имени пользовательского builder. Форма самого builder произвольна: структура
или tuple с параметрами. Значение builder вычисляется один раз. Поддержаны сохранённые локальные
переменные: `let saved = ReaderBuilder(7); computation(saved) { ... }`.
Выбор протокола откладывается, пока тип saved не перестанет быть auto.
Проверки: `test_saved_builder.das`; неизвестный протокол по-прежнему выдаёт
целевую диагностику в `test_saved_builder_missing_protocol.das`.

Макрос в два прохода сначала выводит тип вызова
`ce_protocol(default<BuilderType>)`, затем раскрывает исходный блок. Этот вызов
отсутствует в итоговой программе. Он не получает реальное значение builder;
его тело не предназначено для побочных эффектов. Тип стратегии и элемента
должен определяться типами, а не runtime-настройками. Настройки доступны
перегрузкам операций и `ce_sequence_run`.

## Операции Value и Collect

Ниже `B` — тип builder, `M<T>` — условное обозначение результата с полезным
значением T, а не буквальный синтаксис daScript. Реальные сигнатуры показаны
в `examples/builders/reader_builder.das` и `packages/computation/list_builder.das`.

| Операция | Назначение |
| --- | --- |
| `ce_return(builder, value)` | Упаковать `return value`; для Collect также `yield value` |
| `ce_return_from(builder, source)` | `source \|> return_from`; для Collect также `source \|> yield_from` |
| `ce_unwrap(builder, source) : T` | Только вывести тип переменной bind; вызов не выполняется |
| `ce_bind(builder, source, next : block<(item:T):R>) : R` | Исполнить продолжение нужное число раз или пропустить его |
| `ce_zero(builder)` | Пустой блок, отсутствующая ветка, конец блока без return |
| `ce_delay(builder, body : block<():R>) : R` | Выполнить блок; общий default синхронно вызывает body |
| `ce_combine(builder, first, next : block<():R>) : R` | Соединить вложенный scope/ветку/цикл с оставшимся кодом |
| `ce_for(builder, source, body)` | Необязательный For для одного источника; hook управляет обходом и остановкой |
| `ce_for_zip(builder, arity, traverse)` | Необязательный For с несколькими источниками; visit возвращает false для остановки всего обхода |
| `ce_while(builder, condition, body)` | Необязательный While; condition и body передаются блоками |
| `ce_loop_append(builder, accumulated, step)` | Value: вернуть результат накопления эффектов одной итерации |
| `ce_loop_failed(builder, step) : bool` | Value: остановить цикл при неуспехе |
| `ce_collect_append(builder, var accumulated, step)` | Collect: добавить результат итерации на месте |

Операции требуются только при использовании соответствующей конструкции.
Обычно промежуточные Value-блоки и итерации возвращают `M<CeUnit>`: это
ограничивается перегрузками builder, а не скрытыми проверками runtime.
`ce_bind` получает продолжение и отвечает за семантику остановки/повторения.
Не сохраняйте stack block для последующего вызова: эта стратегия синхронная.

Для Collect результат должен поддерживать перемещение и `inscope`/удаление.
Это не стратегия для обычного `int`-аккумулятора: для такого вычисления
используйте Value. Переопределите `ce_delay` и остальные операции, возвращающие
владеющий результат, с `return <-`.

## Ресурсы

`builder_protocol` публично подключает `computation_resources` с defaults:

- `ce_using(builder, resource, body, cleanup)`;
- `ce_try_finally(builder, body, cleanup)`.

Они подходят для копируемых Value-результатов. Владеющие Collect-результаты
требуют перегрузок с перемещением. `ce_dispose` для конкретного ресурса виден
в модуле вызывающего кода. Cleanup должен возвращать void. Операции выполняют
cleanup после тела и не перехватывают panic: он фатален, см.
[семантика builders](CE_SEMANTICS.md).

## Sequence

```das
struct MySequenceBuilder {}
def ce_protocol(builder : MySequenceBuilder) {
    return ce_sequence_protocol(type<int>)
}
def ce_sequence_run(builder : MySequenceBuilder; var source : iterator<int>) : iterator<int> {
    return <- ce_sequence_protect(source)
}
```

Подключите `sequence_runtime public` в модуле такого builder.
`ce_sequence_run` вызывается ровно один раз при создании CE, до обхода, и
принимает владение сгенерированным итератором. Можно обернуть его с учётом
настроек builder. Обёртка обязана закрывать источник при завершении и отмене;
готовый `ce_sequence_protect` обеспечивает это для обычного
итератора. Возвращаемое значение перемещается наружу.

Bind, yield и resource scopes здесь реализованы общим generator backend;
перегрузки `ce_bind`/`ce_return` Value-стратегии не вызываются. Ограничения
однопроходности, захвата переменных и cleanup описаны в разделах о времени
выполнения, циклах и ресурсах [семантики builders](CE_SEMANTICS.md).
Новый builder внутри этих четырёх стратегий не требует правок ядра. Новая
стратегия исполнения (например, настоящий async scheduler), новый синтаксис
или произвольное переопределение раскрытия AST всё ещё требуют расширения ядра.

## ReaderBuilder

`ReaderBuilder(environment)` предоставляет окружение только для чтения:
`reader_ask() |> bind` получает его, `reader_value(value)` оборачивает обычное
значение, а результат CE имеет поле `.value`. Окружение и результаты должны
быть копируемыми; изменение данных через содержащиеся в них указатели не
запрещается автоматически. Вычисление выполняется сразу: это не отложенная
функция `Environment -> T`. Повторный запуск — новый вызов функции с окружением.
Игровой пример и передача результата между функциями: `reader_demo.das`.

## Проверки

`run_computation.ps1 -Test` включает прежние тесты и новые:

- `test_reader.das`: bind, bind без переменной, return_from, Unit, циклы,
  ветвление, cleanup, однократное создание builder;
- `test_builder_protocol.das`: независимый Collect-модуль, независимый
  Sequence-модуль с другим типом builder, ленивость, завершение, break
  и отсутствие runtime-вызовов ce_protocol;
- отрицательные примеры: нет ce_protocol, неправильный дескриптор,
  отсутствующая операция, несовместимый результат итерации.

`protocol_collect_fixture.das` — независимая тестовая реализация коллекции,
не требующая ListBuilder. Она намеренно повторяет операции списка, чтобы
проверка не могла пройти за счёт импорта встроенного builder.

Для кода с явно квалифицированными именами: `CeUnit` теперь объявлен в
`builder_protocol`, поэтому его полное имя — `builder_protocol::CeUnit`.
Обычное неквалифицированное использование через `require computation`
сохраняется благодаря публичному импорту.

Ещё один независимый модуль — `validation_builder.das`: накопление ошибок
через `validation_zip`, затем обычный bind. Использует только Value-протокол
без изменений фасада или макроса. Пример и контракт: [семантика builders](CE_SEMANTICS.md).

## Источник неподходящего типа

Если у builder нет `ce_unwrap` для источника, bind сообщает об этом одной
ошибкой на строке пользователя и называет оба типа:

```
computation: computation_effects::WriterBuilder cannot bind a source of type
variant<err:string;ok:int>: no ce_unwrap(builder, source) accepts it
```

Устроено это так. Общий `ce_unwrap(builder, source)` из `builder_protocol`
подходит для любой пары и возвращает маркер `CeNotBindable`; более точный
`ce_unwrap` самого builder всегда выигрывает у него при выборе перегрузки.
Маркер замечает тот, кто потребляет источник:

- у builders на продолжениях — стадия bind: она сообщает об ошибке и не
  раскрывает остаток области, поэтому вторичных ошибок нет;
- у прямых builders — `ce_direct_failed`: проверка стоит на строке bind;
- у задач — `ce_await_source`.

У прямых builders и задач остаток области всё же раскрывается, а несвязанное
значение получает тип `CeNotBindable`. Если оно дальше участвует в выражении
(`value + 1`), компилятор сообщит и об этом; сообщение о bind при этом
остаётся. Автору builder ничего делать не нужно: достаточно не определять
`ce_unwrap` с параметром `source : auto`, который принял бы всё.

## Порядок ошибок

Компилятор печатает ошибки в порядке исходного текста, а на одну строку —
одну ошибку со счётчиком остальных. Ошибка в теле computation почти всегда
ломает и код, которым макрос это тело окружает: вызов, несущий остаток области
блоком, не типизируется, пока внутри блока что-то не так. Чтобы эти вторичные
ошибки не шли первыми, макрос ставит такой код в конец computation — на
строку закрывающей скобки:

- вызовы с блоком-остатком (`ce_bind`, `ce_combine`, `ce_delay`, `ce_try_finally`
  и другие) и служебные объявления прямой области;
- внутренний вызов стоит на столбец левее внешнего, поэтому если не подходит
  сам вызов, показана именно его ошибка.

В областях на генераторах (Task, Sequence) переставляются только вызовы
операций builder: имена, которые компилятор даёт вынесенным из генератора
переменным, зависят от позиций, и остальные узлы их сохраняют. `yield`
пользователя сдвигается за своё значение, чтобы жалоба компилятора на сам
`yield` шла после настоящей ошибки в значении.

## Групповой bind

`left |> and_bind(right) |> bind` раскрывается через необязательную перегрузку
`ce_merge_sources(builder, left, right)`. Поддержан стратегиями Value/Collect;
перегрузки добавлены для Result, Option, Validation и List. Источники группы
вычисляются слева направо ровно один раз, даже при неуспешном значении слева.
Контракт, порядок и владение: [семантика builders](CE_SEMANTICS.md).

Для Resumable-протокола группы также проходят через `ce_merge_sources`.
Task-перегрузки находятся в `task_combinators.das`: [семантика builders](CE_SEMANTICS.md).
Макрос сохраняет владение временными источниками при ошибке последующей фабрики.
Bind2/Bind2Return для Task не используются.

## BindReturn

Необязательный `ce_bind_return(builder, source, mapper)` объединяет Bind и
Return. Макрос распознаёт соседнюю завершающую пару, сохраняя пайповый синтаксис.
Без специализированной перегрузки остаётся исходное раскрытие; типовой fallback
не исполняется. Контракт и ограничения: [семантика builders](CE_SEMANTICS.md).

## Bind2Return

Необязательная перегрузка `ce_bind2_return(builder, left, right, mapper)`
оптимизирует внешнюю группу and_bind перед return. Mapper принимает одну
пару first/second. При отсутствии перегрузки сохраняется прежнее раскрытие;
типовой fallback не выполняется. Контракт: [семантика builders](CE_SEMANTICS.md).

## Bind2

Группы and_bind с произвольным продолжением используют необязательный
`ce_bind2` для Result, Option, Validation и List. Синтаксис прежний;
старые builders сохраняют fallback через MergeSources и Bind.
См. [контракт и ограничения](CE_SEMANTICS.md) и `bind2_demo.das`.

Наличие `ce_bind2` проверяется пробным вызовом с продолжением, которое только
возвращает `ce_zero(builder)`; настоящее продолжение подставляется один раз,
в выбранный вариант. Если у builder нет `ce_zero`, hook проверяется самим
продолжением, как раньше. Завершающая пара `bind; return` мала и проверяется
настоящими блоками.

## Прямое раскрытие

Builder, у которого Bind и Combine только обрывают вычисление при неуспехе
(Result, Option, Validation), объявляет `CeDirectProtocol`. Его область
остаётся одним блоком: bind вычисляет источник, при неуспехе возвращает его
как результат области, иначе объявляет значение. `if`, вложенные блоки и
циклы остаются нативными, поэтому ветка может вернуть результат досрочно, а
цикл поддерживает `break` и `continue`. `try_finally` и
`use_resource` по-прежнему идут через операции builder.

Тело цикла раскрывается в ту же область, поэтому хуки `ce_for`, `ce_while` и
`ce_for_zip` у такого builder не вызываются, а `ce_loop_append` ему не нужен.
`for` по диапазону остаётся обычным `for`. Один массив обходится по индексу
под явной блокировкой, остальные источники — через владеющие курсоры; после
цикла блокировка снимается, а источники закрываются.
Внутри цикла результат области не возвращается напрямую: он сохраняется в
переменной области, цикл покидается через `break`, и возврат происходит после
очистки. Тело `try_finally` и область после `use_resource` — блоки,
переданные builder, поэтому `break` и `continue` внутри них записывают, куда
идти, в переменную области цикла и завершают свою область с Unit; так же
завершается каждая область по пути наружу, а тело цикла выполняет команду.

Кроме операций Value-протокола такой builder определяет две:

| Операция | Назначение |
| --- | --- |
| `ce_direct_failed(builder, source) : bool` | Неуспешен ли источник |
| `ce_direct_failure(builder, source, witness : auto(RR)?) : RR` | Тот же неуспех с типом результата области `RR` |

`ce_unwrap(builder, source)` в этом режиме исполняется: он извлекает значение
успешного источника. `ce_loop_failed` проверяет шаг между инструкциями
(`try_finally`, область ресурса) и требует от него Unit.
`ce_bind`, `ce_combine`, `ce_bind_return` и `ce_bind2` при прямом раскрытии
не вызываются. Необязательный `ce_source` применяется как обычно и
вычисляется один раз на источник.

У встроенных Result, Option и Validation операции, которые выполняет bind
(`ce_direct_failed`, `ce_unwrap`), и `ce_return` помечены `[inline]`: компилятор
вставляет их тело в место вызова, и bind стоит одну проверку и одно чтение,
как в ручном коде. Свой прямой builder может сделать так же. Параметр-источник
у такой операции записывается вариантом (`variant<err:string;ok:auto(TT)>`), а
не шаблонным типом (`Result<auto(TT);string>`): экземпляр обобщённой функции
над шаблонным типом содержит псевдоним типа, и с ним тело не встраивается.

Тип результата области в месте неуспеха ещё не выведен: это тип её последней
инструкции. Макрос объявляет в начале области нулевой указатель на этот тип
(`witness`) и получает тип из копии объявлений области, которая только
типизируется и никогда не исполняется. Инициализаторы объявлений поэтому
типизируются дважды.

## Раскрытие по стадиям и пределы вложенности

У builders с продолжениями bind, применение источника и циклы раскрываются
отложенно: макрос оставляет служебный узел, который срабатывает, когда тип
источника уже выведен, и выдаёт ровно один вариант кода. Остаток области не
клонируется в ветки `static_if`, поэтому размер раскрытия растёт линейно от
числа bind и глубины циклов.

Продолжения остаются вложенными блоками, поэтому действуют два предела
компилятора: `max_call_depth` (50 в `daslang.exe`) и `max_infer_passes`
(по умолчанию 50, меняется через `options max_infer_passes`). Один bind
занимает два уровня вызовов и чуть больше двух проходов вывода типов, когда
его источник зависит от предыдущего значения: в одной области помещается 21
такой bind подряд (измерено на WriterBuilder), а с 24 мешает уже глубина
вызовов. Группа `and_bind` занимает около пяти проходов, поэтому подряд
помещается около восьми групп.

При прямом раскрытии вложенности нет, но bind, источник которого зависит от
предыдущего значения, по-прежнему стоит примерно один проход: это значение
получено вызовом обобщённой операции. В одной области помещается 42 таких
bind подряд (измерено на ResultBuilder). Bind с независимыми источниками в
этот предел не упираются: 140 подряд компилируются. Более длинную зависимую
цепочку разбивайте на вложенные CE или функции, либо поднимите
`max_infer_passes`.

## Общий Run и отчёты

Необязательный `ce_run(builder, outcome)` завершает Value/Collect/Sequence CE
и может менять публичный тип результата. Старые builders сохраняют прежний
результат. Отдельный `report_builder.das` превращает Result в отчёт об операции;
пример — `run_demo.das`. Контракт, владение, диагностика и проверки: [семантика builders](CE_SEMANTICS.md).

## Отложенное выполнение

Отдельный модуль `deferred_computation` добавляет `deferred(builder, data) $(snapshot) { ... }` и `run_deferred(task)`. Снимки владеют данными, каждый
запуск получает независимую копию builder/data. Обычный computation остаётся
немедленным. Пример — `deferred_demo.das`; контракт и ограничения — [семантика builders](CE_SEMANTICS.md).

Результат, который продолжает работать после запуска, как задача, участвует в
deferred через два хука; ядро библиотеки ничего не знает о его типе.

- `ce_deferred_payload(result)` возвращает нулевой указатель на тип полезной
  нагрузки: проверяется, что именно она владеет своими данными.
- `ce_deferred_keep(result, cleanup)` делает результат владельцем `cleanup`,
  удаляющего снимок запуска. Задача вызывает его, когда закрывается её источник.

Builder такого результата — фантомный дескриптор: маркер `kind` и нулевые
указатели, которые несут только типы, как `(kind=TaskContext(), element=null)`.

## Отложенный Sequence

Каждый запуск deferred Sequence создаёт отдельный итератор, владеющий снимком
до закрытия. Ресурсы тела закрываются перед удалением снимка. Пример —
`deferred_sequence_demo.das`; контракт — [семантика builders](CE_SEMANTICS.md).

## Переопределение циклов

Подробный контракт, владение источниками и границы: [семантика builders](CE_SEMANTICS.md).
Пример отдельного модуля — `bounded_result_builder.das`. Если hook не определён,
сохраняется прежний fallback через loop/collect append. Для нескольких источников
есть отдельный `ce_for_zip`: [семантика builders](CE_SEMANTICS.md). Генераторная стратегия
Sequence сохраняет native loops.

Наличие `ce_for`, `ce_while` и `ce_for_zip` проверяется пробным вызовом, тело
которого только возвращает `ce_zero(builder)` и потому имеет тип настоящей
итерации. Hook должен принимать такое тело. Настоящее тело цикла подставляется
один раз, в выбранный вариант; если его тип hook не подходит, это ошибка
компиляции, а не переход на fallback.

Путь `ce_for_zip` использует явные курсоры и закрывает источники, когда цикл
завершается или прерывается досрочно. Так же поступают одиночный `For` и
стандартный eager For без hooks. При panic источники не закрываются: он фатален,
см. [семантика builders](CE_SEMANTICS.md).

Общий необязательный `ce_source(builder,input)` адаптирует источники bind, For,
return_from и yield_from до обычных операций и оптимизаций. Контракт:
[семантика builders](CE_SEMANTICS.md). Отдельный builder: `game_source_builder.das`;
пример: `source_demo.das`.

## Коллекции с владением

Move-only List применяет `CeOwnedProtocol`; mutable-reference bind copyable
collection использует `ce_unwrap_borrow` и consuming `ce_bind`. Move-only
Sequence выдаёт временную ссылку из owning-slot iterator. Подробности и
ограничения: [семантика builders](CE_SEMANTICS.md).

## Перемещаемый ресурс

Явное `var r & = source |> use_resource` вызывает `ce_using_move` для eager CE.
Доступна общая реализация с временным mutable borrow и обязательным cleanup;
Sequence удерживает ресурс в heap-ячейке до закрытия дочернего итератора.
Контракт disposer и владения: [семантика builders](CE_SEMANTICS.md).

## ReaderResultBuilder

`examples/builders/reader_result_builder.das` объединяет ReaderAsk и обычный Result через
CeValueProtocol. Реализует базовые операции, MergeSources и BindReturn;
For/While используют общий fallback. Изменения ядра или фасада не требуются.
Контракт и пример: [семантика builders](CE_SEMANTICS.md).

## StateWriterResultBuilder

`examples/builders/state_writer_result_builder.das` объединяет состояние, строковый журнал и Result
через CeValueProtocol. Откат относится к начальному состоянию всего CE; журнал
не откатывается. Циклы и BindReturn используют общий fallback, ресурсные операции
— общий протокол. Подробности: [семантика builders](CE_SEMANTICS.md).

## CoroutineBuilder

`coroutine_builder.das` использует CeSequenceProtocol с CoroutineWait.
`ce_sequence_run` преобразует запросы ожидания в iterator<CoroutineFrame>,
`ce_source` адаптирует дочерние корутины для yield_from. Основной макрос
и фасад остаются прежними. Контракт: [семантика builders](CE_SEMANTICS.md).

## Необязательное накопление List в одном массиве

`ce_collect_sink(builder)` по умолчанию возвращает `CeCollectSinkFallback`.
ListBuilder выбирает `ce_collect_sink_protocol(type<T>)`, разрешая оптимизацию
линейных bind/return-цепочек. Дескриптор сам по себе не заменяет операции
накопления и владения. Полный контракт и ограничения: [семантика builders](CE_SEMANTICS.md).

Resumable builders используют ce_resumable_protocol(type<Event>) и hooks ожидания — см. [семантика builders](CE_SEMANTICS.md). Этот путь не использует eager block-продолжения, которые не могут пережить возврат со стека.

Builder последовательности, который ожидает свои источники, может обходить
ожидаемый источник сам: для этого он определяет хук `ce_await_input(builder, source)`.
Lowerer спрашивает о нём после определения типов; без хука источник обходится
как `ce_await_source(builder, source)`. AsyncSequenceBuilder определяет хук для
Task: тот объединяет адаптацию ожидания и защиту входа в один iterator,
который владеет Task и стабильным слотом события, выдавая изменяемое заимствование.
Слот живёт до завершения всего продолжения bind, включая последующие ожидания.
Специализация обязана закрывать Task при ошибке опроса, отмене и уничтожении
iterator, сохранять сигнал Cancelled и сообщать ошибки cleanup. Пользовательские
реализации `ce_await_source` продолжают использовать обычную защиту источника.
Публичный синтаксис `source |> bind` остаётся прежним.

Для `source |> yield_from` resumable-builder может предоставить
`ce_await_yield_from(builder, source)`: owning iterator своих событий. Общий lowerer
передаёт эти события во внешний producer и закрывает iterator общим
sequence-механизмом. AsyncSequenceBuilder реализует этот hook для дочернего
AsyncSequence того же типа элементов: пересылает pending и some, поглощает
терминальный none, распространяет Cancelled/Failed и владеет дочерним stream.
Скалярные TaskBuilder/TaskResultBuilder такой операции не предоставляют.

Для одиночного resumable For есть optional hook
`ce_await_for_source(builder, source, control)`. Маркер CeResumableForFallback
сохраняет native-обход; iterator событий `{ready, ...}` включает асинхронный путь.
Pending выдаёт `ce_await_pending(builder)`, ready запускает тело с заимствованием
`ce_await_for_value(builder, event)`. Hook возвращает изменяемое заимствование;
lowerer перемещает payload в owning-ячейку итерации, доступную вложенным scopes.
Источник должен закрываться при уничтожении iterator и учитывать break через
`ce_task_loop_not_broken(control)`. Общий lowerer реализует continue и раздельные
control для вложенных циклов. AsyncSequenceBuilder реализует hook для AsyncSequence
любого допустимого типа элемента; тип результата builder независим от входа.

Для нескольких асинхронных источников lowerer сворачивает
`ce_await_for_merge(builder, left, right)` слева направо в пары `{first, second}`,
затем использует обычные ce_await_for_source/ce_await_for_value. Все элементы
раунда перемещаются в одного владельца итерации; имена переменных с учётом
затенения ссылаются на поля вложенных пар. Промежуточные владельцы источников
гарантируют очистку при ошибке последующей фабрики. Fallback сохраняет native zip,
если ни один вход не асинхронный; смешанные/несовместимые входы дают диагностику.
AsyncSequenceBuilder реализует merge как холодный stream с совместным опросом
next и остановкой по кратчайшему источнику, включая отмену всех соседей.
